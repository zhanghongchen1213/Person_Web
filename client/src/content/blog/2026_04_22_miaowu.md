## 写在前面：为啥需要单独一套工具？

救助场景里，**微信群 + 备忘录 + Excel** 是常态——信息一多就乱：今天谁去喂了？这猫换过药没？上月捐款和支出对得上吗？同一只猫要在一堆群里重复讲「它的故事」。

**喵呜档案**想做的，是把「**结构化档案、协作时间线、可审计的账本、分层权限**」收进一个产品里：面向高校社团、小区群、小团队，**不替代你线下撸猫，只把杂事和信任成本降下来**。

---

## 技术栈一瞥

工程上，前端走 **uni-app（Vue 3 + TypeScript）** 一把梭：**微信小程序、H5、App** 共用一套 UI 与业务逻辑，请求统一走 **HTTPS + REST**；后端是 **Java 17 + Spring Boot 3** 的聚合服务，数据落在 **PostgreSQL**，权限上采用 **RBAC 思路** 的多角色模型（主理、铲屎官、喵星人、云守护、游客等），支付与资金相关能力由**支付网关**统一接入——具体路由与配置属于部署范畴，这里不展开。

对读者来说，你只需知道：**三端一个账户、一个 API 面、数据同源**，比「每端各写一坨」要省心得多。

```text
终端：微信小程序 / H5 / App  ←→  REST API  ←→  Spring Boot 业务  ←→  PostgreSQL
                                    ↑
                            支付网关 · 文件存储 等按模块接入
```

## 核心能力

### 1. 图鉴 + 档案：不只是一本「猫咪相册」

**图鉴**里按「喵星 / 区域 / 全国」等维度浏览，点进单猫是**结构化档案**：照片、健康、位置、故事……本质是 **CRUD 友好的领域模型** + 可见性策略（**公开 / 仅队内**），既方便领养宣传，也避免敏感信息裸奔。

![图鉴 - 多维度浏览与单猫入口](https://i.imgs.ovh/2026/04/22/ZNgc8H.md.jpeg)

### 2. 协作打卡：把「时间线」写进产品，而不是写进群公告

多人在同一片区接力时，最怕「我以为你去喂了」。打卡侧支持选猫、选操作（喂养、换水、喂药、TNR 相关等），**带图提交、按日聚合**，在服务端形成可追溯记录——和「在群里发一句」相比，**可检索、可统计、可复盘**是本质差别。

> 小提示：同类操作在同日有**条数上限**（防刷、防误触），产品里会有明确提示；细节以线上一致为准。

![打卡 - 选猫 + 操作 + 提交](https://i.imgs.ovh/2026/04/22/ZNgjcN.md.jpeg)

### 3. 阳光账本：凭证 + 筛选 + 公示

善款最怕「说不清」。账本侧强调 **收支可附凭证、按条件筛选、可生成长图/公示用视图**，让「钱从哪来、花到哪去」在团队与捐赠方之间**对齐事实**，减少扯皮。业务上**零平台抽成、捐款直达主理人**是信任设计的一部分（规则以产品说明为准）。

### 4. 云守护 + 主理人订阅：供给侧、需求侧两条收入逻辑

- **云守护**：低门槛远程参与，与指定 **喵星** 绑定，适合「想帮但不在现场」的人。  
- **主理人订阅**：为创建/管理喵星的一方提供**时长制权益**（如体验/标准/尊享档），和云守护是两条线——一个管「队长的工具箱」，一个管「远方的人的参与感」。

### 5. 我的：角色、个人中心、设置一锅端

**「我的」**里聚合订阅状态、云守护、设置、关于等，对应前面说的 **多角色、多端统一账号**（如 **微信登录** 等），一人一套权限视图，**谁该看啥、能改啥**，在界面上就分流了。

## 谁适合用

| 你的场景 | 可能带来的收益 |
| --- | --- |
| 高校动保、年年换届 | 档案与记录留在**喵星**里，减轻「人走表丢」 |
| 小区多志愿者喂同一片 | **打卡时间线**减少重复/遗漏 |

**小结：** 用 **uni-app + Spring Boot + PostgreSQL** 做底座，用 **RBAC 式多角色** 管住权限，用 **时间线式打卡** 和 **可凭证账本** 管住协作与信任——**喵呜档案**要解决的，是救助协作里**最烦人的信息问题**，不是替代人与猫之间的温度。
